# INTERVIEW READINESS STANDARD — 把任何项目打磨到 postTrain 同等面试就绪度

_写于 2026-07-07。postTrain 能扛住大佬拷打,不是因为结果多大,而是因为它满足下面这套标准。
本文把标准抽出来,任何项目(KIWI 或未来项目)照做即可。末尾附 KIWI 的差距清单。_

---

## 一、七条硬标准(缺一条就有一个攻击面)

### 1. 一段话身份(15 秒能说清"这是什么、为什么难、结果是什么")
不是功能列表,是「问题 → 方法 → 最硬的一个结果 → 下一步」。
postTrain 的模板:"把 Agent 产品的失败行为转成可训练可评测的任务,用冻结考卷跑
SFT/DPO/GRPO 对照,3B GRPO 命中 oracle 后考卷饱和,升级 v0.4。"

### 2. 结果矩阵(所有 claim 收敛到一张表)
行 = 配置/版本,列 = 冻结指标。面试官扫一眼就知道"谁赢了、赢多少"。
**每个格子可复算**:能答"这个数字的分母是什么、在哪个文件、哪次 run"。

### 3. 诚实边界清单(先于面试官说出自己的弱点)
postTrain 有 14 条"不 claim"。规则:**每条弱点必须配一个对应的下一步**
(sim≠real → real anchoring;样本小 → v0.4 扩容)。弱点+计划=成熟;只有弱点=自曝;
没有弱点=撒谎。

### 4. 失败是一等证据(FAILURE_LOG + 机制归因)
每个失败走完整链:**现象 → 排除随机 → 机制 → 归因 → 缓解/停止**。
"停止"要有证据支撑(kill criteria),否则就是 p-hacking。
面试里最强的故事永远来自这里,不是来自成功。

### 5. 决策日志(why 而不是 what)
DECISIONS.md 式:每个有争议的选择记录当时的证据、备选项、判决理由。
这是"代码所有权"拷问的终极防御——你能讲出每个 flag 存在的原因。

### 6. 预注册判据 + 冻结评测
成功标准在动手前写下,事后不许改;考卷冻结,改考卷要走仲裁并给旧版本重打分。
产品项目的对应物:**发布前写下"这个功能成功=什么指标"**,上线后不许换指标。

### 7. 三分钟 pitch + 拷打手册
PITCH_3MIN_zh(带可打断点)+ INTERVIEW_AGENT_HANDBOOK(攻击向量按 kill 概率排序 +
标准答案 + "别说"清单)。**自己先把最狠的问题写出来**,面试官就问不出意外。

## 三、KIWI 按此标准的差距清单(下一个要打磨的项目)

KIWI 已有的底子不差:PROJECT-STATE ✅、预注册文化 ✅(PREREG-20260707/08 两批全闭环)、
设计文档 ✅(KIWI_DESKTOP_COCKPIT_DESIGN)、浏览器端到端验证 ✅。差距:

1. **缺 KIWI_PORTFOLIO_INDEX.md**(标准 §1+§2):一段话身份 + 结果矩阵。
   KIWI 的"结果矩阵"应该是产品指标而非训练指标,现成素材:
   - 截图洪流 MU×3 → 1 张干净卡、1 键批准 3 提案(digest 引擎,已验证)
   - digest 预算/合并规则;BriefBar 状态机(首开→brief;已读→chat+recap)
   - 20% 度量哲学:度量不优化、纯信号、全信源、自用优先(这是差异化立场,面试能讲)
2. **缺 2 分钟 demo 脚本**(产品项目的"pitch"是演示):从打开 /today 到一键批准的
   固定路径 + 兜底截图/录屏(demo 挂了用录屏)。
3. **缺产品版拷打手册**,预写攻击向量:
   - "单用户自用的东西有什么价值?"(答:自用优先是度量哲学不是规模上限;
     digest 的 seen 状态已识别出多用户化的具体改造点——AppSetting 加 user 维度)
   - "并发/状态隔离怎么做?"(DecisionSnapshot 冻结 + request 幂等,bootcamp kq11 已有骨架)
   - "和 postTrain 什么关系?"(bootcamp kq13 已有,双向闭环)
   - "为什么桌面本地优先而不是 SaaS?"(隐私/成本/延迟,与 postTrain 的 API-vs-local 立场同源)
4. **缺诚实边界清单**:数据是自用规模、无外部用户、RSS 管线尚未喂真实持仓/博主源、
   28 条测试期 stale proposals 未清、11 个 live-integration 测试失败(231 非 live 通过)。
   每条配下一步,照 §3 规则。
5. **DECISIONS 薄**:重设计的关键判决(为什么关 batch-1、为什么 digest 而不是过滤器、
   为什么 MemoryPanel 下线)散在 commit 里,应收拢成 why 日志。

**建议顺序**:KIWI_PORTFOLIO_INDEX(半天)→ demo 脚本+录屏(半天)→ 拷打手册(半天)。
三个半天就能把 KIWI 从"能讲"升级到"能扛拷打"。

## 四、给未来任何新项目的开工模板

开工第一天就建六个文件,让"面试就绪"成为副产品而非补作业:

```
PROJECT-STATE.md      # 每次收工更新:做了什么/停在哪/等谁决定
PROGRESS.md           # 叙事日志(round 制)
FAILURE_LOG.md        # 失败即记,带机制归因
DECISIONS.md          # 有争议就记 why
PREREG-*.md           # 动手前写成功判据,事后不改
docs/PORTFOLIO_INDEX  # 身份+矩阵+边界,随里程碑更新
```

纪律三条:数字可复算、弱点先自曝、判据不事后改。
做到了,任何时刻被拉去面试,三天冲刺就够;做不到,三周也不够。
